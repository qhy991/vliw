# PLAN-1000 — the path from 1179 to (a plausible attempt at) 1000

**Baseline:** `explore/merged-floor` @ **1179 cycles** (PSPACE=1). Verified
2026-07-05.

**Target:** 1000 cycles (**−179**, another 1.18× on top of the current 125.30×).

**One-line thesis:** three verified, mostly-independent structural op-count wins
(#15, #16, #18) drop the co-bind floor from 1078 to ~950, an aggressive re-anneal
(#17) cashes ≥ 40 of the ~80-cycle tail gap, and one of the two live moonshots
(#19 §a or §d) covers the last ~50. Any single moonshot succeeding is enough. If
none do, we land at ~1040–1070 — still the biggest single step since #12.

`F = (8·V + A)/60` derivation: alu at 12 slots, valu at 6 slots — co-bind
`max(V/6, A/12) ≥ (2V + A)/24` for allocations that pack both engines. Empirically
the mid-band sits near this bound; the true wall is the max of `F`, load floor, flow
count, plus tail slack.

Two things worth calling out:

- **Movable combines matter only near boundaries.** Interior moves are F-neutral, so
  #14's win came from geometry, not arithmetic. Re-anneal after every op-count change.
- **Flow becomes the wall at k > 23**, so d4 mux is not a "just keep going" lever.

## 2. Why the R1 verdict flipped

`directions/02-hash-opcount.md §5 R1` declared s2+s3 fusion dead in Feb 2026 because
"valu-locked 1→2 raises the binding floor by +512 valu ops." That was **exactly
correct in the 1230-era graph where ALU was binding**. #12/#14 flipped the binding
to valu (alu now has ~105 cycles slack, `RESULT.md` engine profile). In a
valu-bound regime, a valu-locked op is a *pure liability*, and the fusion **deletes**
one per (vec, round) rather than adding one. Same algebra, opposite verdict.

**Rule to bake into future direction reviews:** every "adds N valu-locked ops"
verdict must be re-priced against the current binding engine, not the historical one.

## 3. Parallel exploration plan (one worktree per lane)

All worktrees branch from `explore/merged-floor` at the current HEAD. Correctness
gate on every commit: `python parity_check.py && python algebra_check_ported.py &&
python tests/submission_tests.py` (must print `OK, CYCLES <= 1179`; also
`PSPACE=0 python tests/submission_tests.py` must not regress the fallback).

| worktree | direction | rough time | can start | depends on |
|---|---|---|---|---|
| `explore/15-s2s3-fusion` | #15 | 0.5–1 day | now | — |
| `explore/18-micro-purges` | #18 | 1 day | now | — |
| `explore/17-omni-anneal-infra` | #17 infra | 2 days | now (infra only) | (final anneal after 15+16+18 merge) |
| `explore/16-d4-mux` | #16 | 2–4 days | after #18 lands (needs scratch) | #18 |

Cadence:
1. **Day 1** — spin up `explore/15-s2s3-fusion`, `explore/18-micro-purges`,
   `explore/19a-2round-fuse` (kill test), `explore/17-omni-anneal-infra` in
   parallel. #15 lands standalone; #18 lands standalone; #19a either dies or opens
   a new lane.
2. **Day 2–3** — merge #15 + #18 to `explore/merged-floor`; run #17's SA fast-loop
   from the new equilibrium; start #16 in its own worktree using the freed scratch.
3. **Day 4–5** — merge #16, re-anneal (#17). Trace the resulting schedule; decide
   whether §c (store-broadcast) is worth 1 more day.
4. **Day 6+** — moonshots. §d requires the trace from step 3; §a either produced a
   winning rewrite by now or is dead.

Never let two lanes edit the combine mask / offset vector simultaneously — the
indexing gets clobbered. Emit-order indices renumber after any op-count change.

```bash
  kb.build_kernel(10, 2047, 256, 16); \

  c = Counter(); [c.update(name for name in b for _ in b[name] if name != 'debug') \
                  for b in kb.instrs]; print(c)"
# instrument that engine totals match the direction doc's ± budget
```
Any drift > 16 ops from the predicted delta in a direction doc means the emission
change was wider than intended; investigate before shipping.

## 5. What "success" looks like at each checkpoint

| checkpoint | cycles | how you know |
|---|---|---|
| after #15 alone | 1105–1130 | `submission_tests.py` OK + valu count 6083 ±16 |
| after #15+#18 re-anneal | 1090–1115 | scratch free ≥ 128, floor 1010 |
| after #16 (k=19) + re-anneal | 1045–1075 | load ops < 2000, floor ≤ 1000 |
| after #17 exhaustive anneal | 1030–1055 | tail gap < 40 |
| with #19 §a **or** §d | 990–1020 | one moonshot lands |
| with **both** moonshots | 960–990 | very unlikely; parked as an upper bound |

Land the ceiling estimate honestly. If we hit 1050 and both moonshots die, the
direction ranking says stop — further returns require re-thinking the hash
structure itself (which the algebra proves is nearly rigid: #02 already showed only
K5 is deferrable), and that's a research problem, not an engineering one.
